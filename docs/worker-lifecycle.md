# One-worker lifecycle and recovery

This is an explicitly invoked operator workflow, with pure decision helpers in `workflows/worker-lifecycle.mjs`. It does not run on installation, mod refresh, layout changes, or session startup. Shared selection and acceptance rules remain in installed zstack; first follow [the execution contract](execution-contract.md).

1. Establish authority. Name the durable task ID, coordinator, machine, absolute checkout, owner and exclusive write scope. Record the requested model and effort, permitted actions, concurrency slot, explicit parent or deliberate `--no-parent`, and who will collect and stop the worker. Inspect installed help and capability enforcement before launch. Missing permissions or sandbox capability block the delegated slice; a brief alone is no enforcement.
2. Create a task-owned `.herdr-tasks/<task-id>/` evidence directory. Keep the brief, handoff, command outcomes and task record there; this directory is excluded from revision observation by the record producer. Write the initial record with `records/task-record-store.mjs` as the coordinator, sequence 1, worker null, revision null, receipt null, activity active, and required brief/handoff/artifacts paths. Never give the worker write authority over these records. An isolated scratch checkout is appropriate for a bounded pilot. Preserve all concurrent edits.
3. Write a complete brief before dispatch. Include goal, installed absolute z-mode entrypoint to read first, source context, machine and checkout, exact writable files, prohibited actions, CLI/model/effort, acceptance commands, stop condition and report path. Tell the worker it is independent, is not alone, must preserve other edits, cannot delegate or alter records, and has no implicit commit/push/message authority. Supply no parent controls or credentials. If the report lies inside the checkout, either include it in the tested snapshot or keep it in the evidence directory.
4. Persist `launchAttempted: true` in the handoff **before** invoking `hc run`. Record a unique task-owned terminal name and exact launch argv. Launch one interactive worker with `--bg`, explicit cwd and parent topology; Codex additionally requires `--no-daemon`. Put the initial task in launch argv. Preserve the complete launch response and `first_message.sent`. Do not use auto-approval flags. The verified Codex path uses `--sandbox workspace-write --ask-for-approval never`: denied operations remain blocked, with no automatic escalation. Verify the effective policy and a bounded permission probe rather than trusting flags alone; `on-request` did not override the previous pilot's managed automatic reviewer. A timeout, nonzero exit or transport error is ambiguous: inspect that unique name on the owning machine before deciding whether a process exists. `dispatchDecision` permits no second launch once attempted. A retry needs an explicit fresh assignment after the old writer is confirmed stopped, never a replay of the old journal.
5. Bind the returned machine-qualified address to the actual core epoch and worker occupant/session identity exposed by fresh host evidence. Save that evidence and exact binding in the record. Terminal address, labels, program name, status, screen text or a reusable PID alone do not prove occupant identity. If the host exposes no reliable occupant/core identity, record the gap and leave binding unverified; manual collection can continue, automatic resumption cannot. A false `first_message.sent` permits operator reconciliation of readiness, but no automatic resend; blocked permission decisions remain blocked. A true or unknown delivery result likewise requires inspection before any input.
6. Collect with bounded `hc wait <exact-address> --timeout 30`, then `hc get` and `hc read` or the scoped report artifact. A timeout is a check-in. Idle/done only signals readiness to inspect. Capture blocked checks as blocked, never passing. Account for every task-owned process in the handoff: exact machine/core/terminal/occupant, purpose, scope, last observation, whether it can still write, and collection/stop responsibility. Other terminals are outside scope.
7. Freeze task writers before taking a revision snapshot. Inspect the diff and report, run coordinator acceptance commands, save exact argv/cwd/exit code and output paths, and use `observeRevision(checkout)` before and after verification. Require identical snapshots and bind the record revision and receipt to that tested snapshot. `acceptanceReceipt` requires passing coordinator checks with evidence and the reconciled snapshot; the coordinator must also judge the result against the brief. Never let the worker supply its own acceptance. Dirty work is valid only with the content digest; a commit alone is insufficient. Record accepted, rejected or incomplete through sequence-checked `writeRecord`. Unknown state is incomplete.
8. Clean up only exact task-created occupants after collecting required evidence: reconcile again, then use `hc kill` and `hc rm` for owned terminals when no needed process remains. Confirm termination rather than assuming interruption ended the process. Set activity completed only when work and process accounting are complete. Do not clean up by focus, broad name pattern, or `hc ls` membership.

## Handoff and pickup

Keep a handoff file containing task/coordinator and action authority, explicitly selected execution/mode, absolute checkout/branch, saved commit and dirty digest plus dirty file list, brief/report/evidence paths, launch-attempt and delivery state, each owned binding and writer status, command outcomes, receipt revision, unresolved gaps and the next safe action. Use durable paths; do not save credentials or control tokens. Preserve this before a planned pause. A handoff is evidence, not fresh action authorization for a new session.

Pickup first re-establishes current authorization and observes the owning machine without launching or sending. Reconcile machine reachability, core epoch, terminal address, occupant/session, cwd/checkout, dirty files and `observeRevision` against the saved evidence. Feed this normalized evidence to `reconcile`; `reachable` must mean a successful current query, not configuration presence. If any binding component is missing or changed, the worker is unbound. If the machine is unavailable, record unavailable and preserve the handoff. A surviving worker can be collected after reconciliation; changed revisions invalidate acceptance. Never resend the assignment automatically, even after an app reopen or a saved receipt.

`pausePlan` proposes an interrupt only for the exact currently reconciled live occupant. The operator must recheck identity immediately before control, capture `hc interrupt` and a subsequent observation, then either drain the owned work or leave a clear blocked handoff. If an occupant is ambiguous, do not signal it. Preferences, stopping a turn, stopping a process and durable acceptance are separate actions. Continued background work needs explicit task authority; parentless or `--outlive-parent` execution is never an implicit persistence fallback.

## Recovery checks and proof limits

Run `node --test workflows/worker-lifecycle.test.mjs`. These isolated fixture tests simulate app closure with surviving work, lost core, lost worker, reused address with a fresh shell, stale session, changed checkout/digest and unavailable remote machine. They prove fail-closed decisions and no automatic resend; they do not prove host persistence or remote transport. Live tests must use task-owned processes and isolated `HC_SESSION`/XDG paths for any core shutdown. Never close the user's app, restart their core or kill unrelated terminals to test recovery. Live pilot and host-version evidence belong in [validation](validation.md), with simulation distinguished from actual host observations.

### Native identity mapping

On hc 0.1.15, `server status` exposes a permanent `core.id` and a core PID, while `get` exposes terminal `created_ms`, `pid`, `foreground.argv` and `foreground.cwd`. Permanent core ID is **not** a restart epoch. For the local live pilot, the coordinator observed the exact owned PID's process start time and executable with `ps -p <owned-pid> -o pid=,lstart=,comm=` and separately retained argv/cwd; the binding combines core ID with core process start identity, and occupant PID with process start identity and executable. Compare fresh values immediately before any signal. This is a conservative local observation during the worker's observed lifetime, not a portable session identifier. If process inspection is denied, the remote platform lacks a reliable equivalent, or the process disappeared, leave the binding unverified. Do not replace missing identity with a done badge or saved PID.

### Coordinator record integration

`recordAcceptance(recordPath, {writer, observed, before, after, checks})` reads the existing coordinator record, requires matching before/after/observed revision snapshots, creates a receipt using the exact binding, then writes the next sequence through the locked record store. `checks` contains `{command, exitCode, evidence}` entries captured by the coordinator. This operation does not execute checks or freeze writers: the operator must do those first. Pass freshly collected `observed` data, including machine, checkout, worker binding, reachability, explicit live/finished state and revision. Tests cover rejection without a record update on changed verification snapshots and a successful sequence update. Process cleanup and marking activity completed are subsequent coordinator actions.

The 2026-10-31 bounded pilot used this producer path after the owned worker was stopped and confirmed finished. Its exact-content and write-scope checks accepted a dirty content digest; the task report alone was not used as acceptance. Both the trust-blocked original and its explicitly authorized fresh retry were removed. Scratch directory trust was persisted after specific authorization; plugins/apps and all discovered MCP servers remained disabled, and the launch retained workspace sandbox/on-request flags. The managed UI still displayed custom permissions/Approve for me, so this validates default managed enforcement rather than proving a separate manual-only approval mode. See validation for artifact paths and host limits.
